# faster-whisper 실시간 비교

프런트에서 선택할 수 있는 한국어 음성 전사와 독립 비교 데모입니다. `runner.py`는 겹치지 않는 음성 구간의 확정 전사를 공통 세션에 전달합니다. 별도 `live_demo`는 최근 8초 창을 반복 인식하는 콘솔 비교용이며 세션 이벤트를 만들지 않습니다.

이 후처리는 실험용 휴리스틱입니다. 단어 경계나 인식 내용이 바뀌면 누락·중복·잘못된 확정이 가능하고, 한번 정리된 내용은 다시 수정하지 않습니다. 단어 타임스탬프 산출로 부하도 증가할 수 있습니다. 출력은 콘솔에만 있으며 전사 이벤트나 세션 JSON을 만들지 않습니다. 오디오 창은 메모리에서만 유지합니다.

## 별도 설치

프런트의 선택형 전사는 `runner.py`의 `WhisperLiveTranscription`을 사용합니다. 콘솔 비교 데모와 달리 겹치지 않는 구간을 공통 계약 이벤트(`transcript_final`)로 전달합니다. 구간 처리는 다음과 같습니다(값은 실험값).

- **말 멈춤 분할**(`segmenter.py`의 `PauseSegmenter`): 8초(`min_segment_seconds`) 이상 모인 뒤 말이 0.5초 멈추면 자르고, 계속 말하면 최대 20초(`window_seconds`) 직전 3초 중 가장 조용한 지점에서 자릅니다. Whisper는 구간 길이와 관계없이 30초 입력으로 계산하므로 짧게 자를수록 계산량이 늘고 문맥이 줄어듭니다. 대신 문장이 화면에 나타나기까지 구간 길이만큼(평균 약 11초) 더 걸립니다. 20ms 에너지를 잡음 바닥과 비교한 추정이라 큰 배경음악은 말소리로 볼 수 있습니다. 말소리 프레임이 없는 구간은 모델에 보내지 않습니다.
- **음성 구간 감지**: faster-whisper 내장 Silero VAD(`vad_filter=True`)를 켭니다.
- **지어낸 문장 거르기**(`segment_text`): 구간 전체가 "시청해 주셔서 감사합니다" 같은 알려진 문장 하나인 경우, 줄일 수 없는 반복(압축률 2.4 초과), 무음 확률 0.6 초과이면서 평균 로그확률 -1 미만인 결과, 용어 힌트 목록을 그대로 옮겨 적은 결과를 버립니다. 실제로 같은 말을 반복했을 수 있으므로 남긴 결과의 텍스트는 고치지 않고 인식한 그대로 씁니다("OnClick, OnClick, OnClick" 같은 반복 출력도 그대로 남을 수 있습니다).
- **디코딩 제한**: 온도 0만 쓰고(재시도 없음) 출력은 구간 1초당 6토큰+10으로 제한합니다. 아래 설정 비교 기록의 47초 구간 문제를 막기 위한 값입니다. 실제로 말한 "감사합니다"가 단독 구간이면 함께 빠질 수 있습니다.
- **앞 문장 힌트**: 직전 확정 문장의 끝 120자를 `initial_prompt`로 넣어 문맥과 용어를 잇습니다. 잘못 인식한 내용이 다음 구간에 영향을 줄 수 있습니다.
- **강의 자료 용어 힌트**: 프런트는 준비 화면에 올린 PDF/PPTX에서 여러 쪽에 반복되는 용어(`ai_agent.lecture_terms`, 최대 20개·150자)를 골라 `WhisperLiveTranscription(hint_terms=...)`로 넘기고, 실행기는 이를 faster-whisper `hotwords`로 넣습니다. 자료가 없으면 힌트 없이 동작합니다. 자료에 없는 말을 비슷한 용어로 바꿔 적을 수 있고 처리 시간이 늘어납니다.
- 기본 `beam_size=1`, CPU 스레드 2개입니다.

`WhisperConfig`는 16kHz 입력, 양의 정수 구간 길이·최소 구간·멈춤 길이·빔 크기·청크 길이·스레드 수, 최소 구간 ≤ 최대 구간을 초기화 때 검사합니다. [프런트 안내](../frontend/README.md)를 참고하세요.

### 설정 비교 기록 (2026-11-15, 참고용)

데모 영상(강의 녹화, 고음이 약한 음성) 30~270초를 0.1초 청크로 흘려 넣어 비교했습니다. 정답 자막이 없어 `large-v3-turbo`(빔 5, 전체 문맥, VAD) 전사를 **임시 정답**으로 썼으므로 아래 CER은 실제 오류율이 아닌 설정 간 상대 비교입니다. 영어 용어의 한글 표기 차이("onclick"/"온 클릭")도 오류로 셉니다. 단일 4분 구간·단일 장치(4코어 노트북) 결과이며 다른 프로그램 부하에 따라 처리 시간(RTF)이 0.5~1.3까지 달라졌습니다.

| 설정 (small, int8) | 상대 CER | RTF |
|---|---:|---:|
| 기존: 10초 고정, VAD 없음 | 31.5% | 0.37 |
| 10초 고정 + VAD + 거르기 | 34.0% | 0.48 |
| 말 멈춤 분할 + VAD + 거르기 | 30.2% | 0.53 |
| 위 + 빔 5 | 28.3% | 0.67 |
| 위(빔 1) + 앞 문장 힌트 | 27.7~28.0% | 0.52 |
| 위 + 빔 5 + 앞 문장 힌트 | 31.9% | (부하 중 측정) |
| 말 멈춤 분할 + VAD + 거르기, 스레드 2 | 30.2% | 0.57 |
| base, 말 멈춤 분할 + VAD + 거르기 | 42.3% | 0.27 |

구간 길이 비교(모두 VAD + 거르기 + 앞 문장 힌트, 스레드 2, 구간 길이 외 같은 조건):

| 구간 길이 | 상대 CER | RTF | 평균 구간 |
|---|---:|---:|---:|
| 3~10초 | 28.8% | 0.65 | 6.6초 |
| **8~20초 (기본값)** | **22.6%** | **0.34** | 11.4초 |
| 12~28초 | 22.9% | 0.30 | 15.4초 |
| base, 8~20초 | 42.5% | 0.18 | 11.4초 |

위 표의 3~10초 기본값으로 대시보드 세션(영상 분석 켬, 재식별 끔)에서 데모 영상을 3분 재생했을 때 영상 분석은 약 2.4Hz로 4명 점수를 유지했지만 Whisper RTF가 1.0~1.09로 올라 전사 지연이 37초까지 늘었습니다. 용어 힌트 비교(8~20초 기본 설정). 데모 강의의 실제 자료가 없어 슬라이드에 있을 법한 용어 20개(안드로이드, 액티비티, 추상 클래스, 인터페이스, onClick, OnClickListener 등)를 직접 골라 넣었으므로 실제 자료보다 유리할 수 있습니다. 핵심 용어 수는 임시 정답의 등장 횟수와 비교했고 영문/한글 표기를 같은 용어로 셌습니다. 임시 정답 자체도 "추상"을 "초상"으로 적는 등 틀린 곳이 있어 상대 CER은 힌트 쪽에 불리합니다.

| 설정 | 상대 CER | RTF | 핵심 용어 맞힘(55회) | 용어 오인식("인터뷰"·"주연" 등) |
|---|---:|---:|---:|---:|
| 힌트 없음 | 22.6% | 0.35 | 39 | 10 |
| hotwords 힌트 | 25.8% | 0.55 | 52 | 1 |
| 프롬프트 앞에 용어 | 26.8% | 0.54 | 53 | 1 |

hotwords를 넣은 대시보드 실행에서 Whisper가 한 구간을 약 60초 동안 처리하지 못해 대기열이 차고 0.9초 분량을 버렸습니다. 같은 음성으로 재현하니 "OnClick, OnClick, OnClick" 같은 반복 출력 때문에 faster-whisper 기본 온도 재시도(최대 6회)가 매번 최대 길이까지 다시 디코딩해 8초 구간에 42~47초가 걸렸습니다. 그래서 기본값을 온도 0만 사용(재시도 없음), 출력 길이를 구간 1초당 6토큰+10으로 제한, 힌트 목록을 그대로 옮겨 적은 출력은 버리기로 바꿨습니다. 아래 표는 반복된 단어 묶음을 한 번으로 줄이는 후처리를 함께 쓴 측정입니다. 이후 실제로 반복한 말도 줄어들 수 있어 이 후처리는 뺐습니다(텍스트는 인식한 그대로 사용). 반복 n-gram 금지(`no_repeat_ngram_size=3`)도 시험했지만 정상적으로 다시 나온 말을 바꿔 정확도가 떨어져 기본은 끕니다. 바꾼 뒤 같은 4분 구간 결과:

| 설정 | 상대 CER | RTF | 핵심 용어 맞힘(55회) | 용어 오인식 | 가장 오래 걸린 구간 |
|---|---:|---:|---:|---:|---:|
| 힌트 없음 | 23.5% | 0.56 | 38 | 10 | 13.3초 |
| **용어 힌트 (기본 경로)** | 26.3% | 0.50 | **50** | **1** | **8.1초** |

이 측정은 다른 프로그램 부하가 있는 상태라 RTF가 앞선 표보다 높습니다.

이 결과로 기본 구간을 8~20초로 바꿨습니다. 같은 조건으로 다시 3분 재생했을 때 Whisper RTF는 0.2~0.57, 구간 끝부터 확정 전사까지의 지연은 약 7~8초로 늘지 않았고 대기열 누락은 없었습니다. 영상 분석은 2.2~4.3Hz로 4명 점수를 유지했고 세션 종료는 6.1초 걸렸습니다. 다른 장치, 재식별을 켠 경우, 수업 전체 길이(10분 이상)에서는 확인하지 않았습니다.

같은 구간에서 sherpa 스트리밍 모델은 1분당 0~9자만 출력해 사실상 인식하지 못했습니다. 실제 실행기(`WhisperLiveTranscription`)에 같은 음성을 넣은 확인에서는 3~10초 설정으로 상대 CER 29.6%였습니다(측정 시 CPU 사용률 약 53%, RTF 1.26). 영상 분석과 함께 실행할 때 RTF가 1을 넘으면 전사가 점점 늦어지므로, 데모 중에는 다른 무거운 프로그램을 닫거나 base를 선택하세요.

저장소 루트에서 실행합니다. 별도 Python 3.13 설치가 있으면 `py -3.13 -m venv faster_whisper_stt/.venv`로 만들고, 아니면 `py -m venv faster_whisper_stt/.venv`를 사용합니다. Python 3.14의 `ctranslate2` 휠 제공 여부는 아직 확인되지 않았으므로 3.13을 권장합니다.

```powershell
py -3.13 -m venv faster_whisper_stt/.venv
faster_whisper_stt/.venv/Scripts/python.exe -m pip install --upgrade pip
faster_whisper_stt/.venv/Scripts/python.exe -m pip install -r faster_whisper_stt/requirements.txt
```

## 실행

### 중첩 없는 전사 테스트

`faster_whisper_stt/.venv/Scripts/python.exe -m faster_whisper_stt.direct_demo --source loopback`은 기본 2초 음성 구간을 중첩 없이 한 번씩 인식하여 바로 콘솔에 출력합니다. `--source microphone`은 마이크, `--chunk-seconds 3`은 구간 길이를 변경합니다. VAD, 단어 정렬, 중첩 병합을 사용하지 않으므로 무음 오인식이나 구간 경계에서 단어가 잘릴 수 있고, 모델 자체 처리와 최소 모노 변환은 남습니다. 추론이 밀리면 대기열 길이를 표시하며 최대치에 도달하면 중단합니다. 종료 시 입력 큐에 남은 오디오는 저장하지 않고, 전사 대기열과 마지막으로 받은 짧은 구간은 처리합니다. 프런트·세션 기록에는 연결되지 않습니다.

### sherpa와 동일 입력 비교

두 모델을 한 프로세스에서 실행하므로 비교 환경에 sherpa를 추가로 설치합니다.

```powershell
faster_whisper_stt/.venv/Scripts/python.exe -m pip install sherpa-onnx==2.0.1
faster_whisper_stt/.venv/Scripts/python.exe -m faster_whisper_stt.compare_demo --source loopback --model base
```

기본 출력 장치에서 한 번 캡처하고 모노로 변환한 동일한 16kHz float32 블록을 두 모델에 전달합니다. 마이크는 `--source microphone`, 비교 시간 제한은 예를 들어 `--duration 60`을 사용합니다. 설치된 sherpa 모델 샘플로 장치 없이 확인하려면 `--wav sherpa_stt/models/sherpa-onnx-streaming-zipformer-korean-2024-06-16/test_wavs/0.wav`를 지정합니다. WAV는 16kHz 모노 16비트 PCM이어야 합니다. 종료는 Ctrl+C입니다.

`[sherpa 인식 중]`과 `[sherpa 확정]`, `[whisper]` 원본 가설·정리 전사를 구분해 비교합니다. Whisper는 8초 롤링 창을 재분석하므로 결과가 겹치고 원본 가설은 바뀔 수 있습니다. 종료 시 `[whisper 마지막 창]`은 남은 마지막 창의 별도 추론이며 이전 결과와 겹칩니다. `[공통 입력]`은 입력 레벨과 큐·누락·장치 불연속 및 sherpa 처리 RTF를 표시하고, `[whisper] [처리]`는 창별 추론 시간을 보여 줍니다. 큐 블록 누락이 확인되면 비교를 중단합니다. 장치 불연속이 있다면 두 모델에 전달되기 전부터 오디오가 손실됐을 수 있습니다.

Whisper는 모델 내부 VAD를 사용하므로 모델에 공급한 샘플은 같아도 인식기 내부 처리는 다릅니다. Whisper의 정리 전사는 실험용이고, 두 모델의 최종 발화 확정 방식과 시각 표시도 다릅니다. 시스템 부하 역시 두 모델 동시 실행 조건이며 단독 실행과 다릅니다. 오디오와 전사 텍스트는 파일로 저장하지 않습니다.

```powershell
# 스피커 출력 루프백
faster_whisper_stt/.venv/Scripts/python.exe -m faster_whisper_stt.live_demo --model small

# 마이크 입력 (장치 번호는 기존 sherpa 데모에서 확인)
faster_whisper_stt/.venv/Scripts/python.exe -m faster_whisper_stt.live_demo --source microphone

# 더 빠른 갱신과 짧은 문맥, 선택 프로그램 오디오
faster_whisper_stt/.venv/Scripts/python.exe -m faster_whisper_stt.live_demo --window-seconds 6 --update-seconds 1 --target-process-id 1234
```

처음 실행하면 모델이 `faster_whisper_stt/models/`에 자동으로 내려받아집니다. 기본 `small`/`int8`은 CPU 우선 설정이며, 지원되는 NVIDIA CUDA 환경에서는 `--compute-type float16`을 선택할 수 있습니다. 큰 모델은 지연이 커질 수 있습니다. `--stable-passes 2`는 단어를 정리된 전사에 추가하기 위한 연속 일치 횟수입니다. 실행 환경에 따라 오디오가 쌓여 지연이 증가할 수 있으므로 콘솔의 마지막 추정 지연과 결과 안정성을 sherpa의 개발자 계측값과 함께 비교하세요.

위 `live_demo`는 별도의 비교 데모입니다. 프런트에서는 이 롤링 데모가 아닌 `runner.py`가 겹치지 않는 구간의 확정 전사를 계약 이벤트로 전달합니다.
